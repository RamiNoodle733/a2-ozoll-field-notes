ENGINEERING NOTE / 001

An agent that cannot recover is not autonomous.

It is easy to show an AI agent completing a task. The harder question is what happens when its update fails or its conversation becomes unusable.

A2-OZOLL is an independent project run by Rami Abdelrazzaq. Rami has contributed fixes to OpenClaw; this note looks at two merged pull requests and the broader engineering lesson. It does not claim the current A2-OZOLL machine has been tested against these scenarios.

Failure one: an update should not take down a working gateway

In OpenClaw PR #18131, the update path could schedule a gateway restart even after an update failed. The patch gated the restart on a successful result and added early stops after failed dependency installation or build steps. It also adjusted the doctor step to repair configuration during an update.

The principle is simple: preserve the last working state when a new state fails to install. An automation that needs manual rescue after a routine update has a hidden operating cost.

Failure two: recovery guidance has to be actionable

In OpenClaw PR #12973, the context overflow message was changed to suggest /clear. That matters because a user stuck in an overfull conversation needs an action they can take through the same messaging channel. A vague instruction to reduce input does little when the existing session itself is the problem.

Field rule: For every automated action, define the failure signal, the safe stop, the recovery command, and the evidence that recovery worked.

What to carry into your own agent workflow

  1. Keep a last-known-working path and avoid restarting into partially installed code.
  2. Stop after the first failed stage. Do not cascade a dependency error into a build error and obscure the cause.
  3. Make the recovery command visible where the user encounters the failure.
  4. Record the actual outcome. A scheduled task firing is not proof that its result was delivered or useful.
